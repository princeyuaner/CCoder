# 流式输出卡顿（每帧 48ms → 0.7ms）

日期：2026-09-14　触发：用户反馈「现在输出窗口比较卡」

---

## 1. 症状与真正的成因

用户原话：

> 现在输出窗口比较卡，能先优化这个吗？

时间点很关键：**就在同一天把工具卡片与思考块改成「默认展开」之后**。展开让屏幕上的
DOM 大了好几倍，于是放大了一个一直存在的结构性问题 ——

`includePartialMessages: true` 让逐 token 增量以每 16ms 一批的频率到达（`TranscriptPump`
按 16ms 节流，这一层本来就是对的）。问题在**前端每一帧做了什么**：

| 环节 | 每帧的代价 |
|---|---|
| `Item` / `ToolCallBlock` / `ToolRunCard` / `Markdown` | **完全没有 memo** —— 每来一个字，屏幕上每一张卡片都重跑一遍派生计算（`toolTitle`/`toolDelta`/`toolDiff`/`toolFile`/`toolCommand`/`toolParams`，六个函数**各 JSON.parse 一次参数**），再重建整棵 JSX |
| `toolParams` | **无条件计算**：Write 的参数里装的是整个文件内容，每帧把它 pretty-print 成一大段字符串，然后几乎总是丢掉 |
| 块级元素树 | 正文每长一个字，**全部 841 个块**重建元素并逐节点协调 |

实测（`scene(40)`：40 张卡 + 40 条正文 + 40 个思考块 = 160 项，60 帧）：

```
[perf] items=160 帧=60 合计=2922.3ms 每帧=48.71ms
```

48.7ms/帧 ≈ **20fps 封顶**，而且这还只是 JS —— 浏览器布局还没算。这就是「卡」。

## 2. 三处修法

### 2.1 组件 memo，且让 props 引用稳定

四处 `memo`：`Item`（`Transcript.tsx`）、`ToolCallBlock`、`ToolRunCard`、`Markdown`。

**光加 memo 不够**：原来 `Item` 收的是 `results: Map` / `ended: Set`，而这两个对象
在任何一条工具结果到达时都会换引用 —— 于是一条结果到达会让**所有**项一起失效，
memo 等于没写。改成**精确到那一条**地传：

```tsx
result={row.item.kind === 'toolUse' ? resultsByToolUseId.get(row.item.toolUseId) : undefined}
turnEnded={row.item.kind === 'toolUse' && endedToolUseIds.has(row.item.toolUseId)}
```

同时把卡片里的派生值收进 `useMemo([item.name, item.input])`，并把 `toolParams`
改成**惰性**（`needsParams` 为假就不算）。

### 2.2 正文：复用块级元素对象

分词不是大头：1.5 万字分词 3.1ms，而整帧 25.5ms —— 贵的是**建 841 棵子树并协调**。

React 在协调时如果发现新旧元素是**同一个引用**，会直接跳过整棵子树（官方认可的
children 优化路径）。所以 `Markdown` 里按块缓存已建好的元素，键带上块的原文：

```tsx
const sig = `${token.type}:${token.raw ?? ''}`
const hit = cache.current.get(i)
if (hit !== undefined && hit.sig === sig) return hit.el
```

流式是**追加**的，前面那些块的 `raw` 一个字都不变 → 必然命中 → 每帧只重建最后一个块。

### 2.3 CSS 包含：`contain: layout paint`（卡片/组卡）、`contain: layout`（条目）

JS 不再是瓶颈之后，剩下的是浏览器布局：正文每 16ms 长一点，而卡片都排在同一棵布局树里，
一次重排会把上面几十张展开的卡片一起卷进去。包含让卡片的里外互不影响。

- `.tool` / `.run` 给 `layout paint`：两者**本来就有 `overflow: hidden`**，该裁的早就裁了，
  所以绘制包含不改变任何渲染结果（唯一的 `position: absolute` 元素 `.jump-to-bottom`
  在 `.transcript` 之外）。**不能写 `contain: size`** —— 那会让卡片高度塌成 0。
- `.entry` 只给 `layout`：它没有 `overflow: hidden`，加上 `paint` 会把探出去的东西裁掉。

## 3. 实测数字

| 场景 | 修前 | 修后 |
|---|---|---|
| 160 项 + 逐帧流式（60 帧） | 48.71ms/帧 | **0.73ms/帧** |
| 1.5 万字正文继续流（60 帧） | 25.45ms/帧 | **4.96ms/帧**（其中 3.4ms 是必须做的分词） |
| 布局探针几何（`tool`/`entry`/`scrollH` …） | — | **逐位相同**（摘掉 CSS 再量一遍比对的） |

## 4. 守它的东西

`web/src/streamingCost.test.tsx` —— 三条，**数量断言是主力**：

| 断言 | 守什么 | 退回去会看到 |
|---|---|---|
| 60 帧里 30 张卡片一次都不重渲染 | 组件 memo | `1830`（30 + 30×60）而不是 30 |
| 一条工具结果到达只重渲染那一张卡 | props 引用稳定（不传 map） | `4` 而不是 1 |
| 每帧耗时 < 25ms / 长正文 < 12ms | 整块退化的兜底 | 42–48ms |

两个细节值得记住，都是写歪过的地方：

- **计数器要数"渲染"而不是"重算"**：第一版数的是 `toolTitle` 的调用次数，可是卡片里的
  派生计算被 `useMemo` 挡着，重渲染时不一定重新调它 —— 于是"没重渲染"和"重渲染了但用了
  缓存"混成一个结果，断言变成假的。改用组件体里无条件调用的 `toolStateOf`。
- **验证断言真的会红**：把 memo 依次破坏掉跑一遍，三条全红且数字与注释里预写的完全一致
  （1830 / 4 / 42.3ms）。不验一遍的话，写歪的那版会一路绿着。

## 5. 不做

- **内容虚拟化（`content-visibility` / 只渲染可视区）**：回放 800 条会话时才需要。
  它会让离屏内容按 `contain-intrinsic-size` 估算高度，而"粘底"依赖 `scrollHeight` ——
  估算值一改，视口会跳。收益与风险都要重新量过才谈得上，不在这次里夹带。
  （2026-09-21 复核：滚动跟随那条修订**仍然依赖** `scrollHeight`，这条结论不变；
  顺带把本文档 §6 的数字当依据引用了 —— 暂停判据换成滚轮意图，正是因为
  "我们那笔写入总在同一帧的 scroll steps 之前"，与快慢无关。）
- **改 `TranscriptPump` 的 16ms**：那一层本来就对（一次 `executeJavaScript` 跨一次 CEF
  进程边界，按帧节流是必须的），卡的不是它。
- **流式正文降级成纯文本**：会让 `## 标题`、`**粗体**` 在流式期间原样露出来。
  用户要的是"流式输出看得见"，不是"看得见源码"。

## 6. 事后补量：真实浏览器里到底卡不卡

第 1–4 节的数字**全部出自 jsdom**，而 jsdom 没有布局引擎 —— 它能量
"React 建树 + 协调"，量不到布局、绘制、滚动。`web/tools/perf-probe.mjs`
（`npm run probe:perf`）把同一批场景搬到真实 Chromium 里再量一遍，
量的是**产物**（`dist/`），不是源码。

| 场景 | 帧间隔 p50 / p90 / 最大 | 每帧布局+滚动 | 长任务 |
|---|---|---|---|
| 空转基线（对照物，什么都不推） | 16.7 / 16.7 / 16.8 | — | 0 |
| 空会话流式 | 16.7 / 16.7 / 16.8 | 0 / 0.1 / 0.2 ms | 0 |
| 长会话流式（160 项） | 16.7 / 16.7 / 16.8 | 0 / 0.1 / 0.2 ms | 0 |
| 长正文流式（1.5 万字） | 16.7 / 16.7 / 16.8 | 0 / 0.1 / 0.1 ms | 0 |
| 回放规模（800 项） | 16.7 / 16.7 / 16.8 | 0 / 0.1 / 0.1 ms | 0 |

**两个结论，第二个比第一个重要：**

1. **写探针时的假设是错的。** 当时最可疑的是 `el.scrollTop = el.scrollHeight`
   每帧一次 —— 读 `scrollHeight` 会强制浏览器同步布局，内容越长越贵，这是
   "长会话越来越卡"最经典的产地。量出来 **0.1ms**。假设不成立，滚动策略
   一个字没动。

2. **jsdom 的数字不能外推到真实浏览器。** 把四处 `memo` 全去掉（等于退回
   第 1 节描述的那个状态）重跑，真实 Chromium 里**仍然满帧**：48.7ms/帧
   是 jsdom 的 DOM 模拟器慢出来的，真实 V8 + C++ 布局下，修复前的负载本来
   就在 16.7ms 预算内。

   这不否定第 2 节那三处修改 —— 它们让数量断言从 1830 降到 30，那是
   **不依赖机器快慢**的真实收益，也是这个文件守的主力。但它改变了一件事的
   判断：**如果现在还觉得卡，那不是渲染。** 25ms 那条阈值是"整块退化了"的
   警报线，不是"真实环境会卡"的预言 —— 两者差着一个数量级。

那卡在哪？每帧布局 0.1ms、JS 也便宜，说明屏幕上的字不是被"渲染慢"卡住的，
而是**本来就没到**。这指向另一条线：`sidecar/tools/probe-delta.mjs` ——
增量的**到达**粒度。那个探针按内容块编号记录，专为区分"块间停顿（模型在
思考/调工具，正常）"与"块内停顿（到达真的断了）"而写，结论尚缺。

### 两个踩出来的实现细节

- **不能用 `--virtual-time-budget`。** `layout-probe.mjs` 用它在同一趟里
  拿 `--dump-dom` 的结果，但虚拟时间下 `performance.now()` 与 rAF 都是假的
  —— 性能探针量出来的会是虚拟节奏。所以它改成起本地 HTTP server、页面测完
  `fetch` 把结果 POST 回来，全程真实时间。
- **启动参数与种子节奏都得对。** `--disable-background-timer-throttling`
  那三条缺一不可（headless 默认把"不可见"页面的计时器降频）；种子内容必须
  按生产的 `maxBatch=200` 分批灌 —— 一次推 800 项会造出一个**探针自己的**
  60ms 长任务，那不是产品的行为。探针报的每一条都必须是产品真有的，
  否则它就是狼来了。

## 7. 结论：卡的不是渲染，也不是上游 —— 是我们自己把控制通道灌满了

§6 末尾留下的那个问题（"增量的到达粒度"）在这里收口。

**先排掉上游。** `sidecar/tools/probe-delta.mjs` 跑一次真实提问：

```
#0 thinking  17576 字符  5118 片  28.8s   611 字/秒  → 每 16ms 约 9.8 字
     停顿>300ms: 无
#1 text       1496 字符   743 片   2.9s   510 字/秒
     停顿>300ms: 无
```

上游是**连续**的：每个内容块内部一次 ≥300ms 的停顿都没有。（这正是上一版探针
会误记的那类现象 —— 它把块**间**停顿记成了"最大片间隔"；块间停顿是模型在思考
和调工具，正常。）

**再看我们自己。** 日志里有 4685 条同一句话：

```
读取上下文用量失败：请求超时
```

按秒聚合是**爆发式**的：177 / 311 / 1611 / 157 / 60 / 140 / 906 / 405 / 918。
爆发 = 几千条请求同时躺在 `pending` 里，然后一起超时。

**根因：一行放错了位置。** `ClaudePanel` 的 per-event 分支里：

```kotlin
if (items.any { it is RenderItem.Result }) { setBusy(false); ... }
requestContextUsage()          // ← 在分支外面
```

`requestContextUsage()` 发的是**控制请求**，而控制请求与事件流**共用同一根 stdio
管道**。放在分支外面 = 每一条事件问一次用量：一轮 5861 条事件（上面 5118 + 743）
就是 5861 条 `getContextUsage`。事件流被自己的控制请求挤住，屏幕上的表现就是
"思考走到一半突然停住，过一会儿一大段一起冒出来"。

今天早些时候那条"思考一段一段输出、说一段卡几秒"的抱怨，是同一个根因。

**两处修法**（2026-09-14）：

1. `requestContextUsage()` 搬进 result 分支 —— 每轮一次，本来就是它的本意。
2. `UsageRequestGate`：一次只允许一个在途请求。位置修好之后闸留着的意义，是把
   "再犯一次"的代价从**无上限**压到**一条**；而且多问几次用量本来就没有意义
   （同一秒问两遍，答案只会一样）。

**守它的东西**：`UsageRequestGateTest`（放行 / 在途挡住 / 放闸后可再发）。
"超时也要放闸"那条最容易漏 —— 漏了之后就再也问不到用量，所以单独一条用例。

**怎么再确认**：装新包跑一轮长思考，然后

```bash
grep -c "读取上下文用量失败" ~/AppData/Local/JetBrains/PyCharm2026.1/log/idea.log
```

应该接近 0。屏幕上的思考应当是连续的。
