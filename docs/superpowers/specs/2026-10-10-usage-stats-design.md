# 使用量统计：日 / 周 / 月（V1 仪表盘 + E1 常驻条）

日期：2026-10-10　分支：`v0.2.33-dev`
状态：**已实现**；深色修订见 §7（2026-10-10 晚，用户实机按出）

选型台：`web/tools/usage-view.mjs` → `build/probe/usage-view.html`（三套画法 + 两个入口，
一次性工具，不参与构建）。用户从 V1 仪表盘 / V2 热力图 / V3 账目表里挑的是 **V1**，
入口挑 **E1 常驻条**。

---

## 1. 用户要什么

> 「sdk 支持 token 使用量的统计吗，比如我想看每日每周每月的 token 使用情况」
> →「直接写代码吧。先出个效果图给我选择」→ 选 **V1 + E1**。

SDK 给原料（每次 query 的 `modelUsage` 全量累计 + 每回合一条 result），但**不做持久化、
不做日/周/月聚合** —— 那部分是自己要建的账本。选型台把"管线"和"画法"摆在了一起讲：
三套画法共用同一条数据管线，选的是画法。

## 2. 口径（两个探针钉死的；都在 `sidecar/tools/`）

### `probe-usage-delta.mjs`（真跑会话，本机实测）
- `modelUsage` 是**全管线、跨回合累计**：第 2 回合 = 1+2 的累计 → 落账必须**差分**；
- `/clear` 会把累计**重置**（差分出现下降 ⇒ 当重置、全额取当前快照）；`/clear` 自己
  那条 result **没有 `modelUsage`**（`local_command: "clear"`、turns=0）→ 跳过；
- **resume 从 transcript 里存的总额续走**（第一条 result 就带旧账）→ 有基线时差分照常；
- 崩溃/启动失败的 result 可能是**全零快照** → 跳过**且不能动基线**（动了会让恢复后
  的下一条被当成全额、前面记过的账双算）；
- CLI 对未知模型按 **5/25**（$/M）记费、缓存读 0.1×、缓存写 1.25× —— 我们的单价表兜底
  跟着它走，让 live/fill 两边数量级一致。

### `probe-usage-jsonl.mjs`（只读扫本机，480 文件 / 730 MB / 5.5s）
- assistant 条目 100% 带 `message.usage` + `timestamp` + `cwd` + `uuid`；
- **同一条响应平均重写 2.5 遍**（同 `message.id`、数值一致、不同 uuid，相隔几百毫秒）——
  **按 message.id 去重**，不去重会多算 155%；
- 子代理转写在 `<项目>/<会话id>/subagents/agent-*.jsonl`，同样带 usage（占 6.8%）；
- `requestId` 字段本机全空（去重键里留了位，别指望它）；
- 近 30 天（去重口径）：缓存读占 98.7%，模型绝大多数是网关模型（deepseek 系）。

## 3. 数据层（sidecar）

### 存储 `~/.ccoder/usage/`（整个目录可删，会重建；README.txt 也这么写）
- `usage-ledger.jsonl` —— 一行一笔。`src: live` = 每回合的差分；`src: fill` = 历史回填，
  按 **(天 × 项目 × 模型)** 聚合（同一天多次回填 = 多行，读侧求和）；
- `usage-baselines.json` —— 每会话最后一条快照（差分的基线；旧于 180 天剪掉、上限 5000 条）；
- `usage-backfill.json` —— 回填登记：每文件 `{u: 读到的最后 uuid, m: mtime, mids: 最近 2000 个 message.id}`。

### 规则（`usage.js` / `usage-backfill.js`）
- **差分**：逐模型相减；**任一项下降 ⇒ 重置**（全额取当前）；当前才出现的模型全额；
  基线里有、当前没有的模型**不管**（那是换模型不是重置）；全零快照/无 modelUsage 跳过；
  resume 且**没有基线** → 当基线用（丢一回合，不冒双算的风险）。
- **回填**：mtime 没变整跳；变了从 `u` 之后读；锚丢了（文件被重写）整读一遍、用 `mids` 兜底去重；
  扫描侧按 message.id 去重（同一条重写只算第一遍）；坏行/零用量/无时间戳跳过。
- **项目键归一**（`normalizeProj`）：分隔符统一 `/`、去尾斜杠。**端到端实测抓到的坑** ——
  fill 行的 cwd 来自会话文件（Windows 反斜杠），live 行来自 Kotlin basePath（正斜杠），
  不归一"本项目"会一边有一边没有。写入与比对两侧都归。
- **成本**：读取时按单价表估算（live/fill 同一公式），**不是账单**；数字带 ≈。

### 协议（`index.js` / `Protocol.kt`）
- 命令 `usageReport {scope, project}` → 应答 `usage {id, scope, rows}`（**不需要活会话**——
  账本是磁盘上的文件，同 listSessions 的设计）；
- 推送 `usageTick {project, today, spark}`（每回合一条；没有 id，走 listener）；
- `main()` 起进程就把回填**预热**上（首扫 ~5s，之后增量 ~90ms）；这条请求超时单独给
  60s（`SidecarClient.SCAN_REQUEST_TIMEOUT_MS`），其余请求仍是 10s；
- `createDispatcher` 的 `usageStore` **缺省 null（不记账）**：单测默认路径绝不碰用户真实的
  `~/.ccoder/usage`；生产由 `main()` 显式注入。

## 4. 界面层（Kotlin，`ui/Usage*.kt`）

- **E1 常驻条**（`UsageStrip.kt`）：五张卡之下、输入卡之上一条 28px 矮行；数据两条路
  （Ready 后问一次 + 每回合 tick）；**第一次收到数据之前整条不可见**（BoxLayout 跳过不可见子项，
  不占高度）；点击开对话框。
- **V1 对话框**（`UsageDialog.kt`，620 宽）：粒度分段（按日/按周/按月）+ 口径 chip、三块砖
  （今日/本周/本月，周一起）、堆叠柱（`UsageBars.kt` 自绘）、按模型分解表、[复制 CSV]/[关闭]、
  底部口径脚注。**对话框不碰 sidecar** —— 快照 + 回调，数据由 `ClaudePanel` 去要
  （同 requestContextUsage 的取舍；打开时先摆旧数据、到了再更新）。
  配色**自带两张"纸"**（选型台那两行常量，见 §7）—— 不跟宿主面板色走。
- **纯函数层**（`UsagePeriods.kt`）：分桶（日 30 / 周 12 / 月 12，空洞补零）、三块砖、
  常驻条数据、全局模型顺序与配色（五个一循环，深浅两套照选型台）、成本/变化率格式、CSV。
- 词表：`usage.*` 29 条（中英两份）；`usage.gran/range/scope` 那 8 个键从表里引用、
  不在字面调用点里 → `USAGE_INDIRECT_KEYS` + 对账用例（同 `CONTEXT_ROW_KEYS` 的先例）。

## 5. 刻意不做的

- **V2 热力图 / E2 菜单项**：选型丢了；数据管线在，想要随时长上来。
- **对话框开着时的实时刷新**：tick 只喂常驻条；对话框是"打开即快照 + 换口径时刷新"。
- **按会话/项目的精确成本**：单价表估算一个口径；真账单不在 SDK 的承诺里。
- **thinking tokens 单独列**：它已在 `outputTokens` 里（d.ts 原话），单列反而要防双计。

## 7. 深色修订（2026-10-10 晚，用户实机按出）

**症状**：装进 PyCharm 后对照选型台 ——「效果图背景是灰色的不是全黑」。

**根因**：选型台的深色框画的是"近黑画布上的一张灰卡"（页底 #161719、框底
#2b2d30、砖底 #1e1f22 —— New UI 标准灰）。而用户那套主题（Islands 系）面板
本身就是近黑：截图逐像素取色得到 `getPanelBackground() = #191A1C`（框缘
#151617、标题栏同色；聊天里 diff 删除块的棕色底按 #191A1C 混出来是 #38211B，
实测 #332421 —— 同一出处）。对话框照主题上色 ⇒ 整框黑掉。**选型台那两行
常量是"设计里的灰"，不是主题色** —— 这个区别当初没意识到。

**修法**：统计框自带两张纸（`usagePaletteFor`，值就是选型台那两行）：深
`2b2d30 / 1e1f22 / 393b40`、浅 `f7f8fa / ffffff / d1d1d1`。正文底、三块砖
（补上填充）、分段控件（选中底/外框）、占比条底轨、按钮条（`createSouthPanel`）、
内容窗格与框缘（`recolorWindow` 从 holder 一路上溯）全部换纸；**文字与强调色
仍随主题**。常驻条不动 —— 它长在聊天里，本来就该是聊天的一员。

**两个坑**（都留下注释）：
1. **探针只画过浅色** —— 深色才是用户的日常主题，"深色下整框黑掉"在浅色探针里
   一路过关（"观感的事得离屏看"再进一步：**两个主题都要看**）；
2. 单测环境里 `JBColor.setDark` 翻不动 UIManager 里**已解析**的颜色（深色探针画
   出来和浅色一模一样）—— 深色版要直接按住那几个键（`UsageRenderProbe.pushDarkTheme`）。

**验证**：Kotlin 全量绿（新增"纸是选型台常量"用例）；深色探针逐像素抽查 ——
正文 #2B2D30、砖 #1E1F22；标题栏/按钮条/框缘这三处的实机观感留给装包后的一瞥
（探针够不着平台的窗口部件）。

## 附：执行记录

- 与最初设想的偏离：
  - 落地比选型稿多一处"空态"（一条数据都没有时不画全零的图，只给一句实话）；
  - 按钮叫「复制 CSV」而不是「导出 CSV」——写剪贴板与写文件是两码事，先给前者；
  - 对话框宽度从选型稿的"待定"落成 **620**（`USAGE_DIALOG_WIDTH`）。
- 踩到的坑（都留下注释）：
  1. `Protocol` 的 `num()` 按 **Int** 读，成本 1.5 → 1、0.12 → 0 —— 新加了 `dbl()`；
  2. `Math.round(-5.5) = -5`（向正无穷）—— 变化率要按绝对值舍再补符号；
  3. 给 `request()` 加 timeout 参数时差点放进尾随 lambda 的位置（本仓第三次踩，注释记了）；
  4. 项目键的路径分隔符（见上），是端到端实跑才现形的。
- 数据层的账本目录由端到端实跑创建过（`~/.ccoder/usage`），内容是**真实回填**的
  同一份数据 —— 留着即可，插件首次使用直接就是热的。
