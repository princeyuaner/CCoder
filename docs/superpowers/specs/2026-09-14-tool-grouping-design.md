# 工具调用分组（方案甲「归堆」）

日期：2026-09-14　设计稿：`docs/design/tool-grouping.html` 方案甲

---

## 1. 要解决的问题

用户原话：

> 现在又很多连着的 bash，read，write，是不是可以把他们放一起做成一个卡片，这样没那么乱

一次「读代码 → 改两个文件 → 跑测试」的回合就是八张卡片，一屏放不下 —— 而它们
**本来就是一件事**。设计稿里给了三种画法，用户选了甲：只改「怎么摆」，
不改「长什么样」。

## 2. 目标

- 连续的工具调用并成一张组卡；**点开后里面还是原来那些卡片**（diff、输出、
  状态位一行都不改），只是缩进一级
- 卡面一句摘要（`6 次工具调用 · 读 2 · 改 2 · 跑 2`）+ 涉及的文件（可点，走
  已有的 `openFile` 桥）
- 既有手感一个字不改：折叠只有一层、失败自动展开、输出 14 行封顶、
  卡面只留一行摘要、文件名可点
- **纯前端**：不动协议、不动 Kotlin、不动 sidecar

## 3. 什么算一组：三条规矩

一组 = 一段**连续**的 `toolUse`。

1. **`toolResult` 既不画也不打断。** 它本来就不单独成项（挂在卡片的输出区里），
   而真实顺序永远是「调用 → 结果 → 调用」。不许它打断，否则每组永远只剩一个。
2. **其他任何一种项都打断**：提问、正文、思考、报错、回合结束。它们本身就是
   内容，不是这批动作的一部分。回合结束的 `result` 也在这条里 —— 这正好把
   分组**限制在一个回合之内**。
3. **不足两次的一组原地摊平。** 一张组卡比一张普通卡多占一行、还多一次点击，
   而信息一模一样 —— 阈值就是 2。

## 4. 卡面

- **摘要**：`6 次工具调用 · 读 2 · 改 2 · 跑 2`。分类只影响这句话，**不影响顺序**
  （组内始终按时间排），所以认不出的工具（MCP、以后新增的）落进 `other` 就行 ——
  分错类不会算错，也不会漏画。全是认不出的工具时只有前半句，不写「其他 6」。
- **涉及的文件**：按第一次出现的顺序去重，最多列 3 个，多的折成「+N」。
  **改动规模在整个组里累加** —— 先 Read 后 Edit 是最常见的顺序，只认第一次出现
  会把那次 Edit 的 `+N −M` 丢掉，卡面上就成了「只读没改」（写完用例立刻抓到的）。
- **状态**：跑着 → 转圈 + `已完成 / 总数`；全好 → 打勾；有失败 → 红框 +
  `含 N 处失败`；回合结束还没等到结果 → 已中断。
  **不显示耗时**：回放路径里 `ts` 是推送时刻（Kotlin 侧统一取 `now()`），
  算出来的耗时会撒谎 —— 单张卡片早就有这条规矩（`elapsed.ts`），组卡跟着走。

## 5. 展开规矩

**与单张卡片逐字同一条**：默认收起，只有失败才自动弹开。

设计稿的初稿写的是「跑着的组默认展开」，落地时改成不展开，理由：那等于把"乱"
还回去 —— 一屏又全是内容，而且跑完还不收（自动收会跳），一次会话下来跟没分组
一样。组头自己就带着状态（转圈 + `已完成 / 总数`），"现在跑到第几个"在收起的
状态下一眼可见，不需要靠展开来告知。

失败时：**组弹开，组内那一张失败的卡片自己再弹一次**（`ToolCallBlock` 里同一条
effect），其余几张仍然收着 —— 失败要立刻看得见，但不必把八张卡一起炸开。

## 6. 分层

| 层 | 位置 |
|---|---|
| 分组、摘要、涉及文件 | `web/src/grouping.ts`（纯函数，与渲染解耦） |
| 组卡 | `web/src/components/ToolRunCard.tsx` |
| 接线 | `Transcript.tsx` 把 `items` 换成 `groupRows(items)` 的行 |
| 样式 | `styles.css` 的 `.run*` |
| 布局防线 | `web/tools/layout-probe.mjs`（新增组卡场景） |

**`.run` 必须写 `flex-shrink: 0`。** 它和 `.tool` 一样是高度受限 flex 列
（`.transcript`）的**直接子项**，而 `overflow: hidden` 会把 flex 项的自动最小
尺寸从内容高改成 0 —— 2026-09-13「86 张卡片被压成 2px 细缝」就是这个机制。
探针因此加了一条 `.run` 高度断言，并让组卡出现在两个场景里。

## 7. 验收

- **单测（web）**：`grouping.test.ts`（三条规矩各一条用例、toolResult 不打断、
  result 打断、摘要分类、认不出落 other、涉及文件去重与规模累加）、
  `ToolRunCard.test.tsx`（组头文案、默认收起、展开后是原来那些卡片、失败自动
  弹开且只有那一张标红、跑着转圈、完成打勾、中断收尾、文件 chip 点了调
  `openFile`、超过三个折 +N、没有文件不画那一行）、`Transcript.test.tsx`
  的既有用例全绿（其中「结果按 toolUseId 挂回卡片」那条按新结构多了一次
  "先展开组"的点击）
- **布局探针**：`npm run probe:layout` —— 两个场景都含组卡（收起态与展开态），
  `.run` 高度不得低于 20px（压扁即红），组头宽度正好占满组卡
- **离屏渲染**：探针截图 `build/probe/layout-*.png` 里能看到组头、涉及文件 chip、
  缩进的组内卡片
- **人工**：跑一轮多工具的回合，看组头摘要对不对、点文件 chip 能不能打开、
  失败时是不是只弹开那一张

## 8. 不做

- **不做「按动作类型重排」**（设计稿方案丙）：顺序本身就是信息，「先跑失败还是
  改完才失败」正是人翻转写区要回答的问题
- 不做「跑完自动收起」：会跳，而人正好在看。重开会话回放时组自然是收着的
- 不做组内卡片的新样式（方案乙的紧凑行）：`diff`/输出会因此多一层点击，
  与刚定下的「点开就该看到详情」冲突
- 不改协议：分组所需的 `toolUse` / `toolResult` / `ts` 全在既有 items 里
