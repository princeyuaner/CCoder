# CCoder 会话管理设计 —— 新建与删除

> **这份是 [`session-switch`](2026-09-12-session-switch-design.md) 的续篇，不是替代。**
> 切换那一版已经把会话列表、协议约定、忙时口径定完了（那份的 §3、§4、§5 仍然生效）。
> 这里只加两件在那一版被**明确划出去**的事：那份 §1.3 写着
> 「重命名、删除、打标签…… 都在，但不接」。现在接**删除**和**新建**，
> 重命名与打标签仍然不做。

## 1. 目标与已定的四条

来自设计稿 [`docs/design/session-manage.html`](../../design/session-manage.html) 的四个选择：

| 决策 | 取值 | 理由 |
|---|---|---|
| 新建按钮位置 | 顶部状态栏**最右**，方形图标「＋」，会话标签在它左边 | 420px 那一栏横向真的挤；图标最省地方，语义靠 tooltip「新建会话」补 |
| 删除入口 | 列表行**悬停时**行尾浮出「✕」 | 列表最干净、误点率最低 |
| 删除确认 | **行内二次确认**（该行原地变问句） | 改动关在弹出层里；问句与那一行绑死，不可能删错对象 |
| 删当前会话 | **允许**，删完回到新会话 | 与 session-switch §5.1 同源：「点不动的东西容易被当成 bug」 |

### 1.1 被否掉的方案与原因（存档）

- **右键菜单**做删除入口：最干净，但它是隐藏动作，不右键就永远不知道有删除。
- **模态确认框**：能把「无法恢复」说完整，但插件里要新做一层模态，且整理会话时每次过两道门。
- **直接删 + 底部撤销**：最顺手，但**撤销要求先做软删**（删之前把文件挪走）——
  那是「删除 = 移入回收区」的独立子项目，不是接线。本版不做。
- **重命名 / 打标签**：`renameSession` / `tagSession` 都在，本版仍不接。

---

## 2. 为什么删除必须谨慎：它删的是文件本体

`deleteSession` 在没有 `sessionStore` 时的语义（`sdk.d.ts:566-577` 原文）：

> Without `sessionStore`: removes `{sessionId}.jsonl` and the `{sessionId}/`
> subagent-transcript subdirectory from the local projects dir.
> Throws if the session is not found.

**没有回收站，没有 undo 兜底。** 这是本设计里唯一一处不可逆的操作，
也是为什么「确认」那一条不是礼节而是唯一的闸。

顺带两个必须处理的后果：

- 它会**连子代理记录一起删**（`{sessionId}/` 目录），所以删除文案不能说"只删主对话"。
- 它在**会话不存在时抛错**（而不是静默成功）。这个错误必须如实报出来，
  不能当成"反正也是没了"吞掉 —— 用户会以为删的是另一个。

## 3. 新建会话

### 3.1 语义

就是「换一个空会话」：**不 resume**，走 `session-switch` §5.2 的同一套步骤，
只是跳过 `resumeSessionId`。

**不需要任何确认。** 旧会话不会丢 —— 它照样在列表里，随时能恢复。
加确认反而是撒谎，暗示这个动作危险。

真正的风险只有一个：**你以为在跟旧会话说话，其实已经换了。**
所以这一刻状态栏的会话名必须立刻变成「新会话」，转写区清空。

### 3.2 忙时

与 session-switch §5.1 同口径：`busy == true` 或 `permissionQueue.totalPending > 0` 时，
「＋」**置灰且不可点**，hover 给一行原因（"当前回合还在跑，先按停止"）。

这里与列表的"点了才说"不同：列表是弹出后才说明（因为它有内容可看），
而「＋」是一个单一动作按钮，点了没反应更像坏了 —— 所以它直接置灰 + tooltip。

### 3.3 当前会话 id 的清理

新建后必须把"当前会话"清掉（session-switch §4.4 的两个来源都要清），
否则列表里会有一个**错误的勾**，而且删除时可能删到错的 id。

## 4. 删除

### 4.1 步骤

```
1. 悬停行尾出 ✕（busy 时整片已置灰，见 session-switch §5.1）
2. 点 ✕ → 该行原地变成问句，焦点落在「取消」
3. 点「删除」→ 发 deleteSession
4. 等回执：
   成功 → 该行从列表移除
   失败 → 该行**恢复原样**，并给一行错误说明（不假装删掉了）
5. 若删的是当前会话 → 停会话 + 清转写区 + 起新会话（复用 §3 的路）
```

### 4.2 交互细节 —— 三处容易写错的地方

**(a) ✕ 的点击不能冒泡成"切换会话"。**
整行是可点的（点了切过去），✕ 在行内。不吞掉事件的话，
**点删除会先切过去**，然后你可能正在删一个刚被激活的会话。这是本设计里最危险的一处实现细节。

**(b) 同一时刻只允许一行处于确认态。**
点了 A 行的 ✕ 又去点 B 行的 ✕，A 行必须收回原样。否则界面上会同时挂着两个待确认的删除。

**(c) 焦点落在「取消」。**
与 `PermissionCard` 的既有做法同源（`PermissionCard.kt:26-28`：批准只能显式点击、焦点落在拒绝）。
删除是不可逆的，默认焦点绝不能停在「删除」上。

### 4.3 删掉当前会话

确认语换成**后果说明**而不是"要不要删"：

> 这是**当前对话**。删除后转写区会清空，回到新会话。

删完之后与 §3 完全同路：停会话、清转写区、起新会话、会话标签变「新会话」、列表里的勾消失。

### 4.4 失败路径

| 情况 | 处理 |
|---|---|
| `deleteSession` 抛错（找不到会话） | 该行**恢复原样** + 一行错误说明。**不**从列表移除 —— 那是在撒谎 |
| sidecar 已死 / 没会话 | 同 session-switch §3.2 的待决表终止路径：以失败唤醒 |
| 超时 | 同上，报错；列表行恢复原样 |

## 5. 协议扩展

沿用 session-switch §3.1 的形状与 §3.2 的 **id 回显 + 待决表**：

```
插件 → sidecar
  deleteSession  { id, sessionId }

sidecar → 插件
  sessionDeleted { id, sessionId }      ← 带 id 回显，成功才有

失败走既有的 error 回执（code: DELETE_FAILED）
```

**新建不需要新协议**：它就是 `start` 不带 `resumeSessionId`
（`session-switch` §3.1 已经给 `StartParams` 加了那个字段）。

sidecar 侧转发到 SDK 的 `deleteSession(sessionId, { dir })`。
**没有活会话时也必须能应答** —— 与 `listSessions` 同一条理由：删除是列表上的动作，
不该要求先起会话。

## 6. 测试策略

### 6.1 Node 侧（`sidecar/test/index.test.js`，注入假 sessionFactory，现成模式）

- `deleteSession` 的参数透传；成功回 `sessionDeleted` 且**带 id**
- SDK 抛错 → `error` 回执，**不发** `sessionDeleted`
- 没有活会话时也能应答

### 6.2 Kotlin 侧

`ClaudePanel` 不可单测（`build.gradle.kts:32-35` 不引入平台测试框架），
所以判定逻辑照 `SessionSwitchState.kt` 的做法抽成纯函数：

| 目标 | 用例 |
|---|---|
| `ProtocolTest` | `encodeDeleteSession` 带 id；`sessionDeleted` 解析；缺 sessionId 的 `sessionDeleted` 被丢弃 |
| `SessionListTest` | 悬停行含 ✕；确认态只有一行；**点 ✕ 不触发切换回调**（§4.2a）；「取消」恢复原样 |
| `SessionSwitchStateTest` | 补：busy 时「＋」不可点（§3.2） |
| `SidecarClientTest` | 删除请求按 id 配对；进程退出时以失败唤醒（复用既有用例形状） |

**其中 §4.2(a) 必须有独立用例**：它是本次唯一一个"写错了会误删"的点。

### 6.3 手工冒烟

1. 删一个**不是当前的**会话 → 行消失，`~/.claude/projects/<proj>/<id>.jsonl` 确实没了
2. 删**当前**会话 → 转写区清空、状态栏变「新会话」、列表的勾消失
3. 删一个**已经被终端删掉**的会话 → 明确报错，行**没有**消失
4. busy 时：列表整片置灰、右上角「＋」置灰
5. 悬停到一行行尾 → 点 ✕ → **确认没有先切到那个会话**（§4.2(a) 的冒烟版）

## 9. 改名与标签（2026-09-14 补）

会话列表原本只有三件事：列出来、删掉、恢复。**没法改名，也没法打标签** ——
而列表里的标题是自动摘要（`summary` 取不到就退回 `firstPrompt`），用户多半
想自己起一个。

用的是 SDK 那两个独立函数（`renameSession` / `tagSession`），它们往会话的
存储里写一条记录，**不需要活会话** —— 与删除同一条。

### 9.1 `customTitle` 压过自动摘要

`SDKSessionInfo` 本来就有 `customTitle` 与 `tag` 两个字段，只是 sidecar 当初
"只把界面要用的字段送过线"时没带上。现在带上，并且显示规则是：

```
customTitle → summary → firstPrompt → （占位）
```

**顺序不能改**：用户自己起的名字排在自动摘要后面的话，改完名回到列表看到的
还是那句摘要，等于白改。

### 9.2 入口：双击标题改名、点标签打标签

- **双击标题**就地变输入框。回车提交、Esc 取消、**失焦也提交**（失焦取消的话，
  打完字去点别处那行字就无声地没了）。单击仍然归"切换会话" —— 占用它会把
  切换弄钝。
- **行尾的标签 chip**：有标签显示 `#标签`，没有显示一个淡色的 `＋`。

  没有标签时**也必须留个东西**：改名是"在看得见的东西上加动作"，而"给一个还
  没有标签的会话打标签"没有可点的对象。藏进悬停或右键都会让它找不着 ——
  删除按钮当初从"悬停才浮出来"改成常驻，就是同一个理由（见 §4）。

### 9.3 清空名字 = 恢复自动标题

CLI 把自定义名字单独存在 `custom-title.json` 里，而**读的时候空名字会被当成
"没有"**（SDK 内部是 `eZ(...) || void 0`）。所以输入框清空后回车就是把名字
交还给自动摘要。

清标签同理：`tag` 传 `null`，协议里要**显式**写 JSON null —— 省略字段只表示
"没提这件事"（同 `setEffort`）。

### 9.4 改完回读，不回显

写入之后 sidecar 会调一次 `getSessionInfo` 读回权威值再应答。回读才知道写入
真的落下了；回读失败就退回刚设的值 —— 改是改成了，因为读不回来就报失败是撒谎。

应答只带**变了的那一个字段**（`sessionRenamed` / `sessionTagged` 两个类型），
不带整行：改名不影响 tag，反之亦然，整行回传会让人以为别的字段也可能变了。

界面上仍然**等回执之后才动那一行**（同删除）。它没有删除那种不可逆的分量，
但规矩不变：先改行再等回执的话，写入失败时列表显示的是一个并不存在的新名字。
