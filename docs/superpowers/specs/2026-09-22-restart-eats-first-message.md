# 重开之后发的第一条消息不见了

日期：2026-09-22　分支：`v0.2.25-dev`　`pluginVersion=0.2.25`
状态：**已实现**

---

## 1. 用户报的

> 「切换了不同地址模型，重开了会话后，发出的第一条消息不显示」

## 2. 根因：一次**迟到**的 Reset

换个**端点不一样的**模型时，`options.env` 烤在子进程里、中途改不了，所以那条路走的是
「重开会话」（`pickEffect = Restart`）—— `restartSession()` 起一个**新进程**，
而新进程会带一个**新的 session id** 回来。

问题就出在这个新 id 上：`currentSessionId` 还指着**上一条**，于是新会话的第一条
`init` 被 `isSessionSwitch(current, incoming)`（它当初是给 `/clear` 写的）判成
"换了会话" → **`pushOp(TranscriptOp.Reset)`**。

时间线（用户实际经历的）：

| 时刻 | 发生的事 |
|---|---|
| 1 | 换模型 → 确认框 → `applyModel` + `restartSession()`（`stopSession` 把 `ready` 置 false） |
| 2 | 用户马上敲了第一条消息 → `submit` **先把气泡推上去**，再暂存（`pendingFirstMessage`） |
| 3 | `Ready`（无恢复目标）→ 补发那条消息 ✓ —— 气泡在、消息也发出去了 |
| 4 | 新进程的第一条 `init`（新 id）→ **被当成 /clear → Reset** → 气泡被抹掉 |

用户看到的是「消息不见了」，而消息其实已经发出去 —— 回答照样回来，屏幕上就成了
"只有回答、没有问题"。**为什么偏偏是第一条**：这次 Reset 一辈子只来一次，就在新会话
的第一条 init 上。

同一个根因还吃掉了另一半承诺：`restartSession()` 的文档写的是「fatal 断开后重开：
只换会话，**转写历史留在界面上供参考**」—— 而那条迟到的 Reset 一直在偷偷抹掉它。

## 3. 修法

1. **`restartSession()` 里把 `currentSessionId`（与标题、恢复目标）清成 null。**
   新 id 于是只是被记下来，不再触发切换判定 —— 这也正是 [isSessionSwitch] 自己的
   规矩："`current` 为 null 时不算 —— 全新会话的第一个 init 就是这种情况"。
   顺带：fatal 重开那一档的转写历史**从此真的能留住**（它本来就该留）。
2. **换模型那条路显式清空**（`clearForNewSession()`：转写区 + 标题 + 用量读数）。
   语义是"这段上下文真的没了"（用户刚在确认框里点过），那就**当场清** ——
   迟到的清会吃掉用户在这中间发的消息。这个方法与 `/clear` 那一支**共用一份**：
   两处要清的项必须一致（少清用量，新会话的上下文卡会挂着上一段的读数）。
3. **"回放期间敲的消息"也在回放结束时接上**（顺手修的同一类漏洞）：
   - 会话还没起来就敲 → 走的是"暂存首条"，而从前只有 `Ready` 那一支会补发它；
     恢复会话那条路上 `Ready` 已经过去了 → 那条消息永远发不出去（气泡还被 Reset 抹了）
   - 正在回放时敲 → `busy`，进的是队列；而 `flushQueue()` 只在回合结束（`result`）时
     被调，回放之后根本没有回合会跑 → 队列一直悬着
   两处都收进 `flushPendingFirstMessage(repushBubble)` + `flushQueue()`，在回放收尾调一次。

## 4. 为什么不在 `isSessionSwitch` 里改

它的判据（"同一个进程里 id 变了"）是对的，错的是**喂给它的状态**：我们换了进程，
却还留着上一条会话的记忆。把一个"我们自己的状态没跟上"的错，改成"判据要更聪明"
（比如记住进程代次），只会让那条判据越来越难懂，而且救不了 fatal 重开那一档。

## 5. 验证

- 三侧测试：Kotlin 1666 条、web 307 条、sidecar 214 条，全绿。
- **这一处没有单测**：它全在面板的接线上，而面板起不了（要 Project + JCEF）。
  能钉的纯函数（`isSessionSwitch(null, x) == false`）早有用例；这次改的是**喂给它的
  状态**，那一条只能靠真机 —— 复现步骤就是用户报的那三步：换一个端点不一样的模型 →
  在它重开的窗口里马上发一条 → 那条消息应当留在转写区里，且被正常回答。
