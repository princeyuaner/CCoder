新建与删除

「恢复」那一版已经定了（session-switch.html + spec §5）。 这一页只解决两件新事：右上角怎么放一个新建按钮，以及删除怎么进那个列表。 模拟窗口用的还是探针取到的真实会话数据。

已定的事（不重开）

列表挂顶部状态栏右侧，点开弹出；单行紧凑；不过滤终端会话；恢复语义是 接着写（resume，不 fork）；当前会话打勾。

这次要先认清的一件事：删除是不可逆的

SDK 的 deleteSession 在没接 sessionStore 时，做的是 删掉 {sessionId}.jsonl 和 {sessionId}/ 子代理目录 （sdk.d.ts:566-577）。没有回收站，没有 undo 兜底。

所以下面「怎么确认」那一节不是礼节 —— 它是唯一的闸。而“撤销”那条路要成立， 前提是我们先多做一步软删（删之前挪走文件），那是实打实的实现成本， 在取舍表里标出来了。

三、删除怎么确认

因为删的是文件本体、没有回收站，所以这里选的是「多大的代价换多大的顺手」。 三种做法，代价差别很大。

确认 · A

四、会撞上的三种边界

这三种不解决，功能上线第一天就会被碰到。都是现实里一定会发生的序列，不是假想。

边界 · 01

删的是当前正在用的那个

你正 resume 在会话 X 上，却在列表里把 X 删了。两种处理 —— 左边（禁止）更保守：✕ 置灰，hover 给原因； 右边（允许）更顺：删完立刻回到「新会话」，转写区清空。 允许的那版必须让"转写区被清空"这件事先说，不能删完才让人发现历史没了。

边界 · 02

回合进行中点删除

同 session-switch §5.1 的口径：列表照常弹出，整片置灰 + 一行说明。 理由也一样 —— 拦住比默默允许安全，而"点不动的东西容易被当成 bug"，所以是点了才说。

边界 · 03

新建时当前会话会丢吗

不会。点「新建会话」只是换一个空会话，旧的那个照样在列表里，随时能恢复。 所以新建不需要任何确认 —— 加确认反而是撒谎，暗示它危险。

五、取舍

选择好处代价
A · 图标 ＋ 占最右 最省横向空间，420px 下面板不挤 第一次得猜它是干什么的；要靠 tooltip 补
B · 文字「＋ 新建」 不用猜 长标题会先被挤掉，而标题是这一行唯一认得出会话的东西
C · 进列表首行 新建与历史收在一处，状态栏不加东西 最常用动作变成两次点击，我不推荐
D · 「＋ ▾」合并 常用动作都在一个角 两个"弹会话"的入口挨着，语义要解释
删除入口 · 悬停 ✕ 列表干净；误点概率最低 触控板上发现不了
删除入口 · 常驻 ✕ 一眼可见 20 行 = 20 个删除按钮，吵，且更易误点
删除入口 · 右键菜单 最干净，顺带留了重命名的位置 隐藏动作，得额外教一次
确认 · 行内 不遮挡；问句与那一行绑在一起，不会删错对象 长标题要截断
确认 · 模态 能把「无法恢复」说完整 最重；频繁整理会话时很烦
确认 · 直接删 + 撤销 最顺手，删错可救 要额外做软删（先挪文件再删）；窗口期内 IDE 崩掉就真丢了

看完请回我四件事

  1. 右上角选 A / B / C / D？我倾向 A（图标 ＋ 占最右）—— 420px 那一栏真的挤，而 tooltip 能把"猜"的成本压到最低。
  2. 删除入口选哪种？我倾向 A（悬停 ✕），但如果你自己就常摸触控板，B 更实在。
  3. 确认选哪种？这取决于你多怕误删：B 最安全、C 最顺手但要多做软删。如果选 C，它会变成一个"删除 = 移入回收区"的子项目，不再是接线。
  4. 删当前会话：禁止（置灰）还是允许（删完回新会话）？
