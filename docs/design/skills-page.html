技能（Skills）页 —— 三个界面

在设置里加一页，把 Claude 能用的技能列出来，能禁用、能更新、能打开文件看内容。 这一页不比 MCP 那页 —— 技能条数多、每条短、最主要的动作是"这一条我要不要它"，所以下面三个方案的差别全在 信息密度与开关放在哪。

禁用是 CLI 自己的能力，四档

~/.claude/settings.json 或项目里的 settings.local.json 有一个 skillOverrides 键，值是四档之一 —— 这不是我们发明的开关：

正常（描述进上下文、模型能用、/名字 也能用）· 只列名字（描述不进上下文，省 token，模型仍可调用）· 只我能用（模型看不到，/名字 仍可用）· 关掉（两边都看不到）。

多层设置之间更严的赢（本机 > 项目/用户），有些来源根本不许覆盖（见下）。

写盘走 CLI 自己的写手

改状态不用我们拼 JSON：claude edit-skill-overrides --json， 喂 {"name":"…","state":"off"} 给它，它写进项目本地的 .claude/settings.local.json 并回执 {ok,written,changed}。

这是 VS Code 扩展用的同一条路（子命令藏在 --help 里，写着 "used by the VS Code extension"）。

哪些能关、哪些关不了（已实测）

我的 / 本项目 / 内置 —— 能关。

插件带进来的（frontend-design 那类）—— 关不掉。实测：给 code-review:code-review 写 off，CLI 照写不误（回执 changed:true）， 新会话里它照样在。所以这不是"界面上拦一下"，是根本不该给这颗开关 —— 要停只能停整个插件。

更新 = 三件不同的事

刷新清单（重扫磁盘，秒级）·更新插件（marketplace 拉新版，claude plugin update，重启会话才生效）· 改技能内容（其实就是在编辑器里改那个 SKILL.md）。

三个方案里都在，只是摆在不同的位置。

两个必须知道的实测结果

① 改完要下次开会话才生效。同一个会话里写 off 之后再调一次 reloadSkills()，清单纹丝不动（23 条还是 23 条）；新会话里那条才消失（23 → 22）。

② 关掉的技能从 CLI 的清单里整个消失（totalSkills 一起变）。 所以这页的列表 = CLI 给的清单 ＋ 设置里记着的名字 —— 少了后半截，用户关掉一条之后 再也看不见它、也就开不回来。

推荐

为什么推荐它

  • 一屏 20+ 条：技能是清单，不是卡片。MCP 那页之所以用卡片，是因为一台 server 要交代命令/参数/状态； 技能每条的"独有信息"只有一句描述。
  • 开关在行上：禁用是这页最高频的动作，点一下就该完事，不该开弹窗。
  • 分组的顺序就是重要性的顺序：我的 → 本项目 → 插件 → 内置。用户能改的排前面。
  • 与「模型」页的"列表卡"同一族：左栏 + 分组 + 行，设置里已经有这个先例。

代价

  • 描述只能给一行（省略号）。想看全文要点名字展开或走「⋯ → 打开文件」。
  • 四档里的另外两档藏在「⋯」里 —— 常用两档（开/关）够，冷门两档要多点一下。
四档一眼看全

方案二 · 左列表 + 右详情：把四档摊开讲清楚

左边一列窄的（名字 + 状态点 + 来源），右边是选中那条的详情：完整描述、文件路径、 四档带解释的单选、以及动作。适合"我先看懂这条技能到底干嘛，再决定关不关"。

量过了

这张图下面的四条实测（sidecar/tools/probe-skills.mjs）

问题答案
列表从哪来 reloadSkills()（活会话里问一次，23 条）+ getContextUsage() 里的 skills.skillFrontmatter —— detail:'summary' 就给全（与 full 一字不差）， 每条带 name / source / tokens。
来源都有哪些 真机上量到四种：userSettings(7) · projectSettings(1) · plugin(3) · built-in(12)。左边那三组的标题就是照这四个词写的。
改完什么时候生效 下次开会话。同一会话里写 off 之后再调 reloadSkills()：23 条还是 23 条； 新会话：23 → 22，总量 2,351t → 2,323t。
插件技能能关吗 关不掉。写 off 照样回 changed:true（设置文件里也真写进去了）， 新会话里它照样在 —— CLI 对 plugin 来源直接判 "on"。所以界面上不给开关，只给"停用整个插件"。

探针顺手撞出来的三个坑（实现前必须知道）

  • 关掉的技能从 CLI 的清单里整个消失（不是标成"已关"，是 totalSkills 一起少一条）。 所以列表必须 = CLI 给的清单 ∪ 设置里记着的名字 —— 少了后半截，用户关掉就再也开不回来。 图上那些"已关闭"的灰行就是这么来的（它们没有描述与 token，只能显示名字）。
  • 写盘用设置键，不是显示名。reloadSkills() 给的是显示名（"Debug Issue"、"Refactor Safely"）， 而 CLI 的 skillOverrides 认的是设置键（目录名，插件技能是 plugin:skill）。 拿显示名去写，最坏情况是"回执说改了、实际什么都没有" —— 这一条还没实测， 实现第一步就该验（写显示名 → 新会话看它还不在）。
  • 描述不一定是描述。7 个用户技能里 4 个的 SKILL.md 没写 YAML frontmatter， reloadSkills() 就把文件第一行当描述给了 —— 界面上显示成 <!-- Upstream: https://github.com/… -->。要么原样显示（丑但真）， 要么认出来给一句"这条技能没写描述"。我倾向后者。

顺带一个诚实的判断：这页的价值不是省 token

23 条技能全开，整份清单 2,351 token；单条 26～110。关掉一条省不到 100t —— 拿它当卖点是自欺。 这页真正解决的是"我不想让模型在这件事上用那个技能"：技能是行为指令， 关掉是为了别让 Claude 走偏（比如不想要它的语气、不想让它在你没要求时跑一整套流程）， 顺带才是那点上下文。

这一版我建议做 / 不做

做：列表（分组 + 搜索）· 四档状态（开关 + 「⋯」里的另外两档）· 刷新 · 打开 SKILL.md · 插件技能的"更新"与"停用整个插件" · 从设置补出来的"已关闭"行。

不做：新建技能（那是 claude plugin init，是另一个故事）· 删除技能（删目录，太狠，真要删让用户在编辑器里删）· 技能内容的编辑（那是编辑器的事，我们只负责跳到文件）· 用户级的覆盖（CLI 的写手只写项目本地； 要写用户级就得我们自己去动 ~/.claude/settings.json，那是另一个决定）。

2026-09-30 实现记录

设置里第 8 个页签「技能」。出图：build/probe/settings-skills.png（离屏渲染，数据是这台机器上量到的那份）。

和这张图的三处偏离（都是出图/写码时才发现该改的）

  • 插件行那枚标记从「由插件决定」缩成「插件」：整句要 74px，会把名字那一栏顶到 250px、把描述挤掉 40px。整句改挂在悬停上（tooltip），而行上那句"本地覆盖不了它" 分组标题右边本来就写着一次。
  • 名字那一栏定宽 215px：不定宽的话描述会各自从名字右边开始，一列字参差不齐。 定宽之后先按 190 试，`code-review:code-review` 被裁掉半截——这类"不量不知道"的事 只能靠出图。
  • 描述与 token 之间补了 10px：描述长的时候会一直写到自己右沿，和 token 贴在一起。

实现时定下的两条，比图上多

  • 清单来自一个现起的、不落盘的一次性会话（sidecar/skills-once.js， persistSession:false），不是借正在跑的那个会话。理由是语义： 这页要答的是"新会话会看到什么"，而实测里旧会话改完纹丝不动 —— 借它去读，读到的正是这页要帮用户改掉的那份。另外不落盘是硬要求：插件自己的会话列表 就是扫 ~/.claude/projects/ 出来的，每开一次设置多一条"用户没开过"的会话 比慢几秒严重。
  • 写完立刻重新枚举、核对那条变了没有。没变就在页面上报红： 「写进设置了，但清单里没变 —— 这个名字可能不是它的设置键」。 这是唯一能挡住"回执说成功、实际没生效"的办法，而那个坑是实测过的。

落地时逮到的两个 bug（都不是观感问题）

  • 第一次打开永远不会自动去问：我把"还没问过"和"问完但为空"合成了同一个 Ready，页面用 state is Ready 判"要不要去问" → 永远是 true。 用例逮住的。
  • "skills": null 会让解析器抛 ClassCastException：那是 sidecar 真会发出来的形状（问不到用量时就是它），而 Gson 的 getAsJsonObject 撞上 JsonNull 直接抛 —— 说好的"不抛"没做到。用例逮住的。

真机逮到的第三个 bug：spawn EINVAL

第一版在真机上一打开就一行红字：「问不到技能清单：spawn EINVAL」。链条是： 检测到的 claude 路径是 npm 的 claude.cmd 垫片（这台机器上 %APPDATA%\npm 只有 .cmd / .ps1 / 无扩展名三个垫片，没有 .exe），而 skills-once.js 把它原样交给了 SDK —— SDK 内部用 spawn 调起 CLI， CVE-2024-27980 之后 Node 拒绝直接 spawn 批处理，同步抛 spawn EINVAL （同步，所以连"40 秒没就绪"都没等到；message 里没有路径，所以那一行毫无指向性）。 主会话从不出这个问题，因为 index.js 把路径过了 claude-path.js 的垫片解析 —— 那个文件里 accept() 的注释就写着"返回它只会让问题推迟到 SDK 内部炸成 EINVAL"。

修法：skills-once.js 对 --claude 调同一个 resolveClaudePath（垫片解析只此一份，两处各写各的迟早"聊天能跑、这页说找不到"）。 复现：node sidecar/skills-once.js --cwd . --claude %APPDATA%\npm\claude.cmd —— 修前 {"ok":false,"error":"spawn EINVAL"}，修后正常列出 22 条。 用例 sidecar/test/skills-once.test.js 钉住这个边界。

顺带：失败态顶部还顶着工具行那句「还没有问过技能清单」，和下面「问不到技能清单：…」 自相矛盾（问过了，失败了）—— 真机截图里两条并排出现。现在加载中与失败态 都不再显示那句，只在真的没问过时出现。

这一版没做

新建技能（那是 claude plugin init）· 删除技能（删目录太狠，让用户在编辑器里删）· 技能内容编辑（跳到文件就够了）· 用户级的覆盖（CLI 的写手只写项目本地 .claude/settings.local.json；要写 ~/.claude/settings.json 得我们自己去动那份带密钥的文件，是另一个决定）。
