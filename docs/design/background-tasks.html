后台任务面板做完整，是指什么

今天那张 ⚇ 子代理 卡只回答一个问题——"眼下有谁在跑"。跑完就从表里删掉， 而结局、输出文件、花了多少、正在做什么这些字段，SDK 早就一笔一笔送过来了。 "做完整"= 把面板从在跑清单变成有始有终的账单，再加一个今天完全没有的动作： 把前台阻塞的任务挪到后台（终端里的 Ctrl+B）。

今天

浮层 = runStatus.running 的行，一行一张卡（kind + label），右端 ■ 终止； 对得上子代理记录的才点得开转写。

task_notification 一到就把这条从 byId 里 remove （RunStatusTracker.kt:237）—— 所以"完了没有、成了没有"在界面上是零。

事件流里已经有、只是没画

task_progress：usage{total_tokens, tool_uses, duration_ms}、 last_tool_name、summary。

task_updated.patch：status(跑/暂停/成/败/被杀)、 end_time、error、is_backgrounded。
task_notification：status、summary、 output_file、usage、resource_links。

一行摘要：开关早已打开

agentProgressSummaries: true 就写在 session.js:93。 SDK 的原话：每 ~30 秒 fork 一次子代理的对话，产出一句现在时的描述 （"Analyzing authentication module"），挂在 task_progress.summary 上， 复用模型与 prompt 缓存。MCP 任务则自带 status。

也就是说：这一行数据此刻正在流过来，只是被丢掉了。

今天完全没有的一个动作

Query.backgroundTasks(toolUseId?) —— 把前台正在阻塞的 bash / 子代理挪到后台，等价于终端里按 Ctrl+B：那个阻塞的 tool call 立刻返回 "running in the background"，回合继续往下走，任务照跑，结束时照发 task_notification。

我们没有它：一条 pnpm test --watch 就是把你钉在那儿。

三段的分法
在跑＝task_updated.patch.status ∈ running / pending； 暂停（图里是空的，SDK 有 paused 与 total_paused_ms， 有就单起一段）；刚结束＝completed / failed / killed / stopped。
每行的数字
task_progress.usage 直接给 duration_ms / tool_uses / total_tokens；last_tool_name 就是右端那颗小标（图上那颗 Read）。
一行摘要
task_progress.summary —— 子代理那句我们已经在收 （agentProgressSummaries: true）；MCP 任务用它自己的 status。 取不到时这一行写"正在跑"，不装。
刚结束那一段
每行带结局标记（✓ / ✕ / 停）、用时、一行 summary；右端 看输出（output_file）、子代理还有看转写； MCP 任务若有 resource_links，那儿写"产出文件 N 个"，点开就是那几个文件。
ambient 那行
SDK 的原话：这些管家任务不该进活动指示，但可以出现在任务面板里。 默认折成一行、给个数 —— 别让 live-update 的看门狗把面板刷满。
人数上限
在跑那段照旧封顶（今天 MAX_AGENT_CARDS），多出来的仍是 "还有 N 个在跑"；刚结束只留最近两条，不清空也在下一轮进来时挤掉旧的。

为什么不做成"贴进转写区"
长输出贴进对话会把转写区淹掉，而且它是工具产出，不是对话内容。 浮层是"要的时候才看"的那一档；真要细看，在编辑器里打开（顺手就有搜索、折叠、大文件支持）。
三处边界
① 文件被清掉 → 一行"输出文件不在了（临时目录会清）"，并仍然给"看转写"； ② 文件很大 → 只读末尾 N 行，标题写明"末尾 200 行 · 全文 N 行"； ③ 编码/换行 → 按 UTF-8 读、坏字节替换，不因为一行乱码整屏读不出来。

两个入口，一个动作
转写区的工具卡上（图里），以及面板"在跑"那段的行上 —— 同一颗按钮， 走同一条 backgroundTasks(toolUseId)。
为什么不是"停止"
停止是杀；这颗是换车道。今天的界面上只有杀，于是"这条命令要跑十分钟" 只剩两个选项：等，或者杀掉重来。
失败怎么说
toolUseId 对不上任何前台任务时返回 false（那是竞态： 它刚好自己跑完了）—— 按钮撤掉、卡按正常结局收尾，不弹错。 会话被 CLAUDE_CODE_DISABLE_BACKGROUND_TASKS 禁掉时抛错 —— 那时按钮根本不该出现。
禁用条件
非前台阻塞的卡（子代理里再派子代理、已经结束的、MCP 任务）不给这颗按钮 —— 它没有意义。

三处要跟你已经拍过的板对齐

① "刚结束"那一段，和你 2026-09-24 说过的话是反的。 你当时砍掉的是"查看已结束的"整段历史子代理（一长串、噪声、还要单独发一次请求去磁盘读）—— 词表里那句注（CcoderBundle_zh.properties:405）记着当时的代价：已结束的回看不了转写。

这里要的只有最近这一两次的结局：一条、带输出入口、下一轮就被挤掉。 但我不含糊 —— 若你仍然不要，乙那段直接砍掉，面板保持只列在跑的， 只留"一行摘要 + 看输出 + 放到后台"这三样（那三样与那个决定不冲突）。

② perTaskStopAffordance 是个要拍板的开关。 今天不声明它：点「停止」= 中断这一回合，后台任务跟着一起被杀。 声明它（SDK 的原话是"宿主自己渲染了逐个停的控件"）：中断只收这一回合， 后台任务留着，由面板逐个停。我们其实已经有逐个停的按钮了 —— 但要不要把"停止"从"全杀"改成"只收这一回合"，是产品决定，不是 SDK 决定。

③ ambient 会改变"有没有在跑"的口径。 task_started.ambient 与 background_tasks_changed[].ambient 是 SDK 明说的"别拿它当活动指示"的那些（看盘、live-update 看门狗）。 今天我们没有这个字段的概念，卡上的数很可能把它们也算进去了 —— 接面板时顺手把卡面的计数改成 非 ambient 的在跑数。

落地分四步（每步都能单独发一版）

  1. 行上补数据：RunStatusTracker 已经收着 task_progress / task_updated —— 把 usage、last_tool_name、 summary、patch.status 存进 RunningTask， 面板两排就能画满；结束的那条别 remove，标成结局。
  2. 看输出：output_file → 浮层读末尾 N 行 + 在编辑器里打开； 文件不在了说实话。
  3. 放到后台：协议加一条 backgroundTasks（照 stopTask 的写法）， 转写区工具卡与面板行两个入口；false 当竞态处理。
  4. 两个开关拍板：perTaskStopAffordance（停止的语义）、 "刚结束"这一段要不要 —— 我的建议是要，但只留最近两条。

真机上要看的三件（无头环境验不了）：面板在有 5+ 条时的高度与滚动； output_file 在 Windows 上的真实落点与生命周期（谁清的、多久清）； ambient 任务在真实会话里的数量级（会不会一开就有五六条）。
