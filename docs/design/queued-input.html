排队输入：跑着的时候还能接着敲

它还在跑，你想起一句话要补 —— 今天按回车什么都不会发生。 下面是三套做法，以及六条决定了它们差在哪的事实（全部来自探针实测， 不是推断）。

先说六条事实

01

今天回车是被吞掉的

ClaudePanel.kt:387 那行 if (busy) return —— 回合进行中不发送，理由是"按钮那时是停止，发送键却另发一条会让两者语义打架"。 功能的口子就这一处：输入框本身没禁用，鼠标没有第二条路。

02

CLI 自己就收，而且折进当前回合

A 跑着的时候推 B、C：一个 result，一段回复，里面答了 A完成 / B-OK / C-OK。不是"等这轮跑完再单起两轮"—— 你补的话被当成同一回合的追加指令。

03

顺序保得住

B 在 C 前发，回答里 B-OK 也在 C-OK 前。没有乱序 —— 排队不需要我们做排序。

04

但一个回执都没有

事件流里没有任何"已收下 / 已折入"的信号；自己盖的 uuid 也不出现在 result 上（uuid=-）。 界面上的"排队中"只能靠本地推断，协议给不了。

05

撤回：SDK 面上没有入口

interrupt() 返回 undefined（这个 CLI 的 system/init 上 capabilities=null，没有 interrupt_receipt_v1），拿不到 still_queued； 单条撤回的 cancel_async_message 也没被 SDK 暴露。

06

打断不会清掉排队的

D 跑着时排 E，打断 D 之后 E 照样跑了（新的 init、E-OK、各自一个 result）。 所以"停止"必须自己定义对排队的处理 —— 否则用户点了停止，还会看见进度条又动起来。

一、三套做法

方案 甲

照直透传

删掉 if (busy) return，其余一个字不动。B、C 立刻进 CLI， 按终端里那套原生语义折进当前回合。

代价 两个用户气泡长得一模一样，分不出哪条还在排队； 撤回没有入口；「停止」之后排队的还会接着跑（事实 06）， 看起来就是"停止没停干净"。

方案 乙 · 推荐

插件侧排队

忙时回车只入队、不发送：消息停在插件里，等这一回合的 result 到了再自动发出去。队列是我们自己的，于是 "排队中""撤销""停止时一起清掉"全都成立。

落地后又改了一处（2026-09-15，用户原话：「排队的信息大于 1 条应该 转成一个列表，点击后展开，不然太占用空间了」）：一条直接把内容写在 那一行上（排队 1 · 正文 ✕），两条以上收成一行 排队 N ▸、点开才是列表。下面这张 mockup 画的是改之前的样子。

乙的规矩不变，只是"排队"这件事也要能用鼠标干 —— 停止键左边多一个发送键，忙时点它 = 入队。

二、逐条对比

问的事甲 · 透传乙 · 插件侧排队丙 · 乙 + 按钮
忙时按回车 立刻发给 CLI，折进当前回合 入队，回合结束自动发 同乙
排队中看得见吗 看不出 虚线气泡 + 工具栏计数 同乙
能撤回吗 不能（事实 05） 能，✕ 一下 同乙
点停止之后，排队的 照跑（事实 06）—— 看着像没停干净 一起清掉，气泡标「已取消」 同乙
与终端手感 一模一样 第二句各起一回合（终端是折进去） 同乙
协议 / sidecar 改动 零 零（Protocol.encodeSend 原样用） 零
Kotlin 改动 一行 队列 + 状态机 + 三处收尾（停止 / 断线 / 切会话） 乙 + 一个按钮与其状态

我建议：乙。丙 的那颗按钮先不做

甲 的那一行改动看着最省事，但它把最难的三件事全留给了用户： 哪条还在排队看不出来、撤不回来、点停止之后它还会自己跑起来。 最后那条尤其难受 —— 事实 06 说的不是极端情况，是每次打断都会遇到。

乙 之所以成立，是因为 CLI 的队列不在我们手里，我们才需要自己拿一个： 消息停在插件里，撤回和"停干净"就都是本地动作，不必求 SDK 给我们口子 （它也没给，见事实 05）。

丙 的那颗发送键是可选的后续：如果抬手流用了几天发现"忙时只会按回车" 不够用，再加它 —— 加它只动工具栏那一行，不推翻乙的任何一条规矩。

①停止 = 连队列一起清，气泡变灰写「已取消」而不是消失（转写区只追加，是我们一直在守的规矩）。
②flush 的判据用 result（现有代码里 setBusy(false) 就是它）。待确认：一个任务里会不会出现"中间 result"——若会，排队就得等真正的收尾那条。
③断线 / 切会话 / 重启：队列跟着清，气泡标「已取消」。会话都换了，把上一段的指令发到新会话里是灾难。
④不做条数上限：工具栏那个「排队 N」就是全部信息。要拦也是拦"排队里又发命令"这类越界情况（/ 开头的照样排，不特殊对待）。
⑤等待期间输入框照旧可编辑、可补全、可按 ↑ 取历史 —— 排队的只是"发出去"这一步，不是输入区。
⑥待确认：事实 05 里"没有 interrupt_receipt_v1"是推的 —— 探针读到的是 system/init 上 capabilities 这个字段为 null（字段名可能另有其名）。实测到的只有 interrupt() 返回 undefined 这一条。
