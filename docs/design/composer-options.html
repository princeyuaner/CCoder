三个方案

同一块区域、同一批控件、同一份主题变量 —— 只有构图哲学不同。 下面每个稿子都能点进去真的打字，聚焦态是真的（:focus-within）， 因为输入区好不好看，一半在于聚焦时它怎么回应你。

参考 · 每格数据从哪来

三个数字，三个不同的 SDK 来源。

上下文  12.3k / 200k · 6% ◐ 3/7修复 extractor 指纹2▾

数据来源

  • 3/7 与清单 ← TodoWrite 的 tool_use input（todos[].status）
  • 正在：… ← 同为 todos 里 status=in_progress 那项的 activeForm
  • 子代理数量 ← background_tasks_changed，整集替换而非加减
  • 子代理行 ← task_started（类型/描述）+ task_progress（token/时长）
  • ambient=true 的必须滤掉，否则指示器永远不归零

子代理完工后不留在条里，而是回到转写流，作为嵌套块挂在触发它的那个 tool_use 下面——运行中是状态，产出是历史。 这需要 sidecar 打开 forwardSubagentText: true（默认关），光改 Kotlin 侧做不到。

怎么选

三个方案都躲开了同一个陷阱：把边框画在输入框本身。现在这版之所以生硬，是因为一个 1px 直角矩形直接框住了文字，像表单字段而不像对话输入。

A · 卡片式B · 内嵌式C · 提示符式
边界靠什么圆角描边底板色差 + 顶沿亮线上方一条硬分割线
聚焦的回应描边变蓝顶沿点蓝提示符发微光
上下文放哪容器内顶部，成 pills工具栏右侧，纯文字底部状态行，等宽
模型切换以后放哪底部左，独立按钮底部左，幽灵按钮状态行第一段
再加控件的成本低（工具栏还很空）低低（状态行可续段）
窄栏表现边框变密最好好，但中文密
"分不清"的风险最低最高低
Swing 实现量中（圆角自绘 ~40 行）最小（≈ 现状 + 焦点监听）小（提示符就是 JLabel）

我的建议：选 A。它正面解决你提过的"分不清"，同时把模型切换和上下文都安排进了容器内部 —— 你后续要加的东西，位置现在就已经留好了。 C 是最有想法的那个，但它的成败押在"中文等宽小字号好不好看"上，值得你实机比对一次再决定要不要冒险。

进度条 / 百分比为真实算法（取 modelUsage 中输入量最大的一项除以 contextWindow）。 圆角、投影、过渡在 HTML 里是免费的，在 Swing 里不是 —— 上面每一处标注了实际代价。
