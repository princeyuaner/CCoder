工具调用长什么样

你原话是「bash 没有显示详情，编辑文件没有显示正在编辑哪个文件」。 现在每一条工具调用都是同一个可折叠块，标题写着「工具：Bash」， 点开是一坨缩进过的 JSON —— 命令、文件路径、参数全在里面，只是没人替你读出来。 下面三套是把它做成"一眼能读"的三种画法，都摆在 420px 的真实宽度里。

三条事实 —— 它们决定了三套画法差在哪

  • 工具的参数本来就全都有。每条 tool_use 带 id、name、input： 命令在 input.command，文件在 input.file_path，搜索词在 input.pattern。 所以「Edit 在改哪个文件」不用改任何后端就能显示，把 JSON 读出来即可。
  • 但工具的输出根本没到界面上。结果是另一条消息（tool_result，靠 tool_use_id 配对）， 而插件现在把这类消息整个丢掉了 —— MessageRenderer.renderEvent 只认 assistant / result / system / stream_event。 要看 bash 的 stdout，必须动管线（Kotlin 新增一种渲染项 → 协议 → React）。
  • Edit 的结果是一句废话。它只回 "has been updated successfully"， 改了什么只能从 input 里的 old_string/new_string 自己算 diff（纯前端就能算）。 Read 的结果才是真内容（文件正文，带行号）。
现在长这样
工具：Bash 
{
  "command": "git log --oneline -15 && git branch --show-current",
  "description": "Show recent commits"
}

同一段真实对话（就是今天那轮：Bash 查 git 日志 → Read 读 ClaudePanel → Grep 搜字段 → Edit 改测试文件），在三种画法下的样子。带 ▸ 的地方是真能点的。

二、四个躲不开的细节

这些不分方案，选哪套都得定。左边是我建议的答案，右边是反例 —— 你不同意就直说。

长输出：默认折叠

输出 · 214 行

建议折叠。跑一次测试能刷出几百行，转写区会被淹掉、上面的对话全被顶走。折叠后仍写着行数，"有没有东西"一眼知道。

失败：红边 + 首行输出

Bash gradlew test ✕ 失败 
› 3 tests failed

失败必须自己冒出来，不能靠用户点开找。用 is_error 判定，红边 + 摘一行原因。

diff 的来源

− 旧的 old_string
+ 新的 new_string

从 input 算，不看 result。Edit 的 result 只有一句 "updated successfully"，没有内容；Write 更直接 —— 全文就在 input.content 里。

"正在编辑 xxx"

◐ Edit SessionSwitchState.kt 正在生成参数…

能做，但要单独加钱。模型是一个字一个字吐出参数的，要实时显示文件名得解析流式增量（现在这类增量被刻意忽略）。不要它也行 —— 参数生成完那一瞬间卡片就出现了。

三、要改哪些文件

方案Kotlin（插件）协议 / 共享契约React（界面）测试
甲 · 一行标题 不动 不动 新增一个纯函数（读 input 出标题）+ 行组件；ToolCallBlock 改写 纯函数单测（Vitest）
乙 · 标题+折叠 RenderItem.ToolResult + 渲染映射（认 user 事件里的 tool_result） 要加：shared/transcript-ops.json 多一种 item 标题解析 + 输出块 + diff 块 + 按 toolUseId 把结果挂回对应的工具 两侧都要（契约测试：任一端改了另一端就红）
丙 · 步骤流 同乙，另加流式增量解析（"正在生成参数"） 同乙 转写区整体重排（气泡 + 轨迹混排、状态点、耗时） 同乙 + 轨迹状态的单测

我建议乙

你抱怨的两件事，根因是同一个：参数和结果都没被读出来。「在编哪个文件」不改后端就能做，但「bash 没有详情」要的正是输出 —— 而输出必须动管线，甲绕不过去。

丙更好看，但它的代价不在画法、在重排：现在转写区是"一条一条往下摞"的线性结构，气泡、工具、结果行各占一行； 改成轨迹意味着所有既有条目都要重新定位，420px 宽里也换不回多少密度。乙 把丙 最值钱的那部分（diff 预览、失败冒头）先拿到手， 将来想升级到轨迹，乙 的组件还能直接用。
