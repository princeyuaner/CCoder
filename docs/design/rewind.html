文件回滚：界面该长什么样

spec（2026-09-15-rewind-presets-mcp-design.md 第一章）已定了形态：每条本会话发出的用户消息挂一个 ↺， 点击弹确认框，框里两段 —— 将要恢复的文件清单 与 一句语义说明。 这份图把那两段画实，并把规格没写死的几处摊开问。

约束一

清单不能来自 SDK：探针事实 5 —— filesChanged 恒为空（dryRun 回 []、真回滚回 null）。 只能从转写区自己算：那条消息之后的 Write / Edit / MultiEdit 工具卡。

约束二

回滚连这条消息自己的改动一起撤销，且之后新建的文件会被删掉； 但对话一个字都不变（rewindFiles 只动文件）。三件事三句话，少一句就是让用户误解。

约束三

resume 恢复进来的历史消息没有 uuid（不经我们的 send）—— 挂上 ↺ 却点不动比不挂更糟，所以历史消息不挂。

规格没写死、这张图也没替你定的四处

问题 两面 图上的倾向
1. ↺ 悬停浮出还是常显？ 悬停：干净，但"可回滚"这件事藏起来了，第一次用不知道有这功能。
常显：一排灰 ↺ 挂在每条消息边上，长会话里很吵。		 倾向悬停——产品先例同源（会话列表的删除 ✕ 就是悬停浮出），且回滚是低频动作。
2. 清单标「会被删除」吗？ 标：最重的后果直接进视线。
不标：转写区只能推断新建，标错一行伤信任。		 倾向先不标（B″），删除只在那句话里说 —— 探针事实 5 的教训：拿不到的就是拿不到，不装。
3. 默认焦点与按钮色 此刻图上：焦点在「取消」（回车不执行），「回滚」是主按钮蓝 —— 但它会删文件。 倾向焦点留「取消」（与权限框「回车不批准」同规）；「回滚」要不要换 danger 红，待定。
4. header 里那句「此操作不可撤销」 留着：说清没有退路。
删掉：rewindFiles 不留痕、也确实没有 undo，但同一颗 ↺ 可以再点一次回滚到别的消息 —— 有点像"能退"，容易说岔。		 倾向留着，但把它降级成正文里的半句，不占 header 徽章的位置。
