工具卡片：进行中 · 完成 · 失败

读写文件、跑指令这些工具，在还没跑完的时候给个"在动"的信号，跑完了给个确认。 下面是三套画法 —— 以及三条决定了它们差在哪的事实。

先说三条事实 —— 它们决定了三套画法差在哪

01

「真进度条」做不到

工具不报进度。SDK 流里那个 input_json_delta 是模型在生成参数， 不是工具在执行 —— 拿它当进度条等于撒谎。 所以能画的只有两种：不确定态（转圈 / 流动条纹），或者已耗时。

02

「进行中」不用动协议

toolUse 到了、配对的 toolResult 没到 —— 就是进行中。 卡片组件本来就收着 result?，undefined 即未完成。纯前端推导，零改动。

03

但「进行中」可能永不结束

被拒绝、被中断、会话被杀掉的工具不会再收到 result。 不收尾就是永远转圈 —— 得有一条确定性的收尾规则（见下方细节 ②）。

一、三套画法

方案 甲

转圈 + 绿勾

最贴近你原话的一套：跑的时候转圈，跑完打勾。状态位在最右，固定 12px，切换不挤动标题。

转写区

方案 乙

底沿流动条纹

把"进度条"画在卡片底沿，不占横向空间；完成时整条变绿。420px 里最省地方的一套。

转写区

▸B Bash npm run build
▸R Read web/src/components/ToolCallBlock.tsx
▸B Bash gradlew test 失败

方案 丙

转圈 + 已耗时

在甲的基础上多一个秒数。这是唯一能回答"它是不是卡住了"的画法 —— 一个读文件转 30 秒，光看圈是看不出来的。

转写区

二、四种状态并排看（以甲为例）

第四种状态是必须有的一条 —— 否则被中断的工具会永远转圈。它不分方案，选哪套都得画。

进行中
完成
失败
已中断

三、四个躲不开的细节（不分方案）

细节我的答案反例（为什么不能那样）
状态位要占住位置 右侧固定 12px，任何状态下都占位。完成态只是换个图形，宽度不变。 不占位的话，卡片从"转圈"变"打勾"的瞬间整行文字会左右抖一下 —— 一次会话里几十次。
永不结束的收尾 收到回合结束的 result 事件时，把还没配上结果的卡片一次性标成"已中断"。确定性、可单测。 不处理 → 永远转圈；用超时（比如 60s）→ 一个真跑了 90 秒的构建会被误判成中断。
回放历史全是一片勾 完成态做得低调：勾用低饱和绿、不描边、不加底色。回放 78 条时是一片安静的 ✔，不吵。 给完成态加底色或动画 → 打开历史会话像一棵圣诞树。
等你操作时也在转 接受。权限询问、AskUserQuestion 期间卡片本来就该是"没结束"，旁边另有卡片在问。 想区分"在跑"和"等你"要动协议（SDK 不告诉你工具卡在哪一步），那是另一个工程。

四、要改哪些文件

方案Kotlin（插件）协议 / 共享契约React（界面）
甲不动不动ToolCallBlock.tsx、styles.css、Transcript.tsx（传"回合是否结束"）
乙不动不动同上（状态位换成底沿条）
丙不动不动同上 + 卡片内一个 1 秒定时器（只跑在"进行中"的那张上）

三套都不改 Kotlin、不改协议 —— 状态是前端从已有的两条消息推出来的。 Transcript.tsx 那处改动是把"回合是否已结束"传给卡片，用来做中断收尾。

我建议丙

你要的其实是两件事："它还在动" 和 "它跑完了"。甲的勾回答了第二件， 但转圈只回答了"没结束"—— 一个卡死的圈和一个正在跑的圈长得一模一样。 丙多出来的那个秒数，正是把这两者分开的唯一信息，而它几乎不花钱（卡片里一个定时器，不动协议）。

乙 我不推荐：底沿那条在 29px 高的卡片上太细，而且"完成 = 变绿"不如一个勾一眼确认； 它唯一的优势是省横向空间，但 420px 里挤掉的是标题的省略号空间，不划算。

丙的一个已知代价：回放历史时算不出真实耗时（回放路径的两条消息 ts 都是回放那一刻）。 所以历史里只显示勾、不显示秒数 —— 这反而正好，历史里你也不关心当年那条命令跑了多久。

01选哪套 —— 甲 / 乙 / 丙？（我押丙）
02完成态的勾要不要配一句文字（完成）还是只有图形？（我押只有图形）
03"进行中"的卡片要不要自动展开，露出命令 / 参数？（我押不展开 —— 那是另一件事，今天不做）
